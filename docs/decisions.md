# Decisions

1. **SQLite prototype over PostgreSQL+Supabase** — spec §3 allows SQLite for a single-machine prototype; `DATABASE_URL` keeps PostgreSQL open. Avoids running two backends.
2. **Hand-rolled CSS design system instead of Tailwind/shadcn** — fewer build dependencies for a hackathon slice; same visual/UX requirements (large targets, one accent, accessible focus). Revisit if the design system grows.
3. **Adapters return labelled simulated results without `META_API_KEY`** — the full loop stays demoable and testable; `simulated` is stored and rendered so nobody mistakes it for a live model result. Live request/response schemas must be re-verified against current official Meta docs before enabling (see ai.py comments).
4. **Header-based demo identity** — fastest role demo (technician/expert/reviewer); explicitly not production auth.
5. **Lexical manual search, no embeddings** — per spec §6.2; deterministic, offline-friendly ranking by term frequency with source snippets.
6. **Jobs pin the approved version ID** — later approvals supersede for future jobs only; active/offline jobs never change underneath a technician.
7. **Tutorial Studio edits canonical content, never rendered artifacts** — the Markdown guide, snapshots, drafts, MP4s, and approvals are all downstream of `tutorial_jobs.steps/materials/transcript`. Saves create immutable `tutorial_content_revisions` and bump `content_revision`; publishing happens only through explicit regeneration, which snapshots (never overwrites) and syncs or forks the Review draft. Chosen over direct Markdown editing so the guide can never disagree with the structured procedure.
8. **Guide-regeneration dedup respects locks and content revisions** — an identical format generation within 120s returns the existing snapshot (double-click protection), but the dedup is skipped when the linked draft is locked or `content_revision` advanced since the snapshot, so post-approval edits always fork a new revision instead of silently reusing.
9. **Video versions are append-only rows** — each render creates a new `video_guides` row (`version_number` increments) with its own MP4; scene-plan edits land on a `draft` row until rendered. The voiceover stays a cut of the original recording (validated ranges, no synthesis), so captions can never imply changed narration.
10. **Four primary destinations** — Workbench, Procedures, Tutorials, Activity; Review/Manuals/Settings are secondary. Guided job stays a contextual mode, not a nav item; Activity is the single job-history destination (the old History view renders the same Activity content).
11. **Stage rollup is computed, not stored** — `GET /api/tutorial/{jid}/stages` aggregates ProcessingEvents into pending/running/completed/failed/skipped/needs_review with per-stage live/simulated/mixed mode. No new state machine on the job row, so events stay the single source of truth and the UI can never disagree with the timeline.
12. **Canonical step identity covers reviewer-visible fields** — `_canon_list` includes title, instruction, expected result, verification notes, and tools, so expert edits to those fields participate in 3-way sync/conflict instead of being silently overwritten. Old snapshots get empty defaults so the first post-upgrade sync compares like-for-like.
13. **Field feedback is a validated event, proposals are drafts** — `field_feedback` events validate step IDs against the pinned revision (unknown IDs rejected); `propose-improvement` (reviewer+ only, finished jobs only) creates a new draft with before/after in `source_evidence.proposal`, never touching approved versions. Simulated proposals only quote the technician's words and are labelled low-confidence.
14. **Crop quality is flagged, never auto-fixed** - `_illustration_quality` detects empty masks, tiny crops, frame-edge cutoffs, extreme aspect ratios, and missing context; flagged crops stay visible with a recovery note (re-track/tap) rather than being silently dropped or regenerated.
15. **Offline grants are HMAC capabilities, not a second auth system** - `fg-grant.*` tokens reuse the `SECRET_KEY` signing scheme from `auth.py`, bound to procedure + exact version + actor + 30-day expiry. They authorize exactly one thing: registering an offline-started job against a since-superseded revision. Draft/rejected versions, other procedures, other actors, and expired grants are all rejected.
16. **Sync diagnostics persist per item in IndexedDB** - the report (`meta.sync-report`) survives reloads; entries clear only when their item later syncs or the user explicitly discards an unrecoverable one after a confirmation dialog. Dependent events/photos/finishes wait for their job registration instead of being submitted against a missing session.
17. **Tutorial uploads stream to disk, never fully into RAM** - chunked copy to a temp file with an incremental sha256, size cap enforced while receiving, atomic rename on success, temp cleanup on every path. Duplicate detection needs the full hash first, so the temp file exists briefly in all cases.
18. **Visual-first is a strategy, not a separate pipeline** - one `run_job` branches on assessed speech sufficiency; visual-first reuses segmentation, guide, draft, review, and video stages unchanged. Candidate steps carry `evidence_frames`, `confidence`, and `derivation: visual` so every downstream surface can distinguish observation from narration.
19. **Large uploads are chunked and resumable end-to-end** - 4 MB offset-addressed PUTs against an upload session (`POST /api/tutorial/uploads`, `GET` status, `POST complete` with SHA-256 verification, `DELETE` abort, 24 h sweeper). Retries re-send only unconfirmed bytes; the complete call atomically creates the identical `TutorialJob` a single-shot upload would. The browser never holds more than one chunk plus a streaming hash in memory.
